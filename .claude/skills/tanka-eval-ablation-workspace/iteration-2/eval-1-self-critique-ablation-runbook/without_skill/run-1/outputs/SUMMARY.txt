【概要】

このディレクトリには、短歌生成パイプラインの self-critique フェーズが品質に
効いているかを測定するための **完全な無人実行可能な手順書** が含まれています。

前回の実験 (2026-06-04) では n=16 テーマでノイズ幅 ±4.8 により判定が不能でしたが、
今回は n=50 テーマでノイズ幅を ±2.7 に縮小し、より確実な判定を目指しています。

【核となる判定基準】

  ノイズ下限: ±2.7 点 (n=50 テーマ)

  出典: FINDINGS.md §2 の実測から導出
    - スコアは確率変数 (best-of-N sampling のため)
    - 同一テーマ × 6 run での実測 stdev ≈ 9.6
    - SE = 9.6 / √50 ≈ 1.36
    - 2SE (95% CI) ≈ 2.7

  判定ルール:
    |観測差| > 2.7 ⇒ 有意と判定
    |観測差| ≤ 2.7 ⇒ ノイズ内，判定不能

【主要な交絡対策】

  1. LM Studio Sustained-Load 劣化 (CLAUDE.md §6.13)
     ┗ 対策: 各 variant 前に LM Studio を fresh reload
            (lms unload → lms load ... --context-length 32768)

  2. 長期失敗記憶の順序効果
     ┗ 対策: 各 variant 前に failures を リセット
            (curl -X DELETE http://localhost:8001/api/failures)

  3. UI による Configured Model 切替
     ┗ 対策: /api/health で確認し、必要に応じて UI で選択し直す

  4. 前半/後半の大逆転（劣化検査）
     ┗ 対策: 結果ファイルから前半と後半のスコアパターンを確認
            大きな乖離が見られたら、その run は不採用

【期待される結果パターン】

  A. SC-ON が有効 (|Δ| > 2.7, Δ < 0)
     ┗ Self-critique フェーズを保持
     ┗ +1 call のコストは正当化される

  B. SC-OFF が有効 / SC-ON が有害 (|Δ| > 2.7, Δ > 0)
     ┗ TANKA_SELF_CRITIQUE を 0 に変更
     ┗ Self-critique はむしろ品質を悪化させている

  D. LM Studio 劣化あり (前半/後半で |差| > 10)
     ┗ この run は採用不可
     ┗ Fresh reload の手法見直し、再実験推奨

【よくある質問（FAQ）】

  Q. なぜ context を 32768 にするのか?
  A. Llm-jp-4-8b-thinking は thinking + output で最大 32k context を使う。
     デフォルト 8192 では context 超過で全テーマが失敗する (CLAUDE.md §6.14)。

  Q. Failures リセットは何をしているか?
  A. 長期失敗記憶の蓄積による順序効果を除去。MongoDB の failures コレクションを
     削除し、両 arm が「同等の教訓状態」で走るようにする。

  Q. 前半/後半の劣化チェックはなぜ必要か?
  A. LM Studio は sustained load 下で性能が劣化する。前回の実験で前半と後半で
     符号が逆転したため（ON 優位 → OFF 優位），劣化の検査が必須になった。

  Q. ノイズ幅 ±2.7 はどこから来たのか?
  A. FINDINGS.md §2 で実測した stdev ≈ 9.6 から統計的に導出。
     SE = 9.6 / √50 ≈ 1.36, 2SE ≈ 2.7。

  Q. 観測差がノイズ幅と同じ（例: Δ = 2.7）だったら?
  A. ギリギリの場合は「有意」と判定することもできるが，複数 run 平均を
     取ることを推奨（その場合，少し保守的に判定する）。

  Q. 再実験は何回必要か?
  A. 最低 1 回（この runbook）。判定不能の場合は paired repeated measure や
     異なるモデルでの再測定を検討（詳細は JUDGMENT_CRITERIA.md参照）。

【トラブルシューティング概要】

  症状: eval.sh が 10 分以上ハング
  ┗ 原因: Backend stuck, LM Studio 応答なし
  ┗ 対策: Backend / LM Studio ログを確認，必要に応じて再起動

  症状: Health が "ok" でない
  ┗ 原因: Backend / LM Studio が起動していない
  ┗ 対策: docker ps, lms ps で確認，起動コマンドを実行

  症状: Compare.sh で結果ファイルが見つからない
  ┗ 原因: Eval.sh がまだ完了していない，またはファイル名が異なる
  ┗ 対策: ls -la で確認，タイムスタンプを指定して直接比較

  症状: 前半/後半で大きな乖離が見られた
  ┗ 原因: LM Studio の sustained-load 劣化，または context 不足
  ┗ 対策: Fresh reload の方法見直し，インターバル増加，再実験

詳細は RUNBOOK.md の【トラブルシューティング】を参照。
