## Step 1: 観測差の算出

### 1.1 Compare.sh の出力から抽出

```bash
cd /Users/nrm176p/GitHub2/LLM/app/backend/eval
./compare.sh sc-on sc-off
```

出力例:
```
[ 品質指標 ]
  初回合格率                 37.5% -> 6.2%  (-31.2%) [劣化]
  総合合格率                 56.2% -> 56.2%   (0.0%) [=]
  平均 attempt 数             3.56 -> 3.50  (-0.06) [改善]
  平均最終スコア             75.06 -> 79.75  (+4.69) [改善]  ← ここ
  plateau 率                 43.8% -> 43.8%   (0.0%) [=]
```

**抽出: 平均最終スコアの行を見つけ、括弧内の値を取得**

```
Δ = +4.69 点
```

### 1.2 符号の解釈

```
Δ = avg_final_score(sc-ON) - avg_final_score(sc-OFF)

Δ > 0  ⇒ sc-ON が高い ⇒ self-critique は有効（効果あり）
Δ < 0  ⇒ sc-OFF が高い ⇒ self-critique は有害（効果マイナス）
```

## Step 2: ノイズ下限との比較

### 2.1 事前登録したノイズ下限

**n=50 テーマの場合**: ±2.7 点

出典: FINDINGS.md §2
```
同一テーマ × 6 run での実測:
  stdev ≈ 9.6
  SE = 9.6 / √50 ≈ 1.36
  ノイズ幅 (2SE) ≈ 2.7
```

### 2.2 判定ルール

```
|Δ| > 2.7?

YES  ⇒ 有意と判定 → 次のステップへ
NO   ⇒ 判定不能 → 結論「観測差はノイズ内」
```

### 2.3 判定例

#### ケース 1: Δ = +4.69 (sc-OFF が高い)

```
|4.69| > 2.7?  → YES, 有意

Δ < 0?  → YES (OFF が高い)

結論: SC-OFF が有意に優位。self-critique は有害。
```

#### ケース 2: Δ = +0.5 (sc-ON がやや高い)

```
|0.5| > 2.7?  → NO

結論: 有意差なし。ノイズ内の差。判定不能。
```

#### ケース 3: Δ = -3.8 (sc-ON が高い)

```
|−3.8| > 2.7?  → YES, 有意

Δ < 0?  → NO (ON が高い)

結論: SC-ON が有意に優位。self-critique は有効。
```

## Step 3: 前半/後半の劣化チェック

### 3.1 なぜこのチェックが必要か?

前回の実験 (FINDINGS.md §5.5) で判明：
- Blocked A/B で sc-ON の 前半 vs 後半 で **逆転** 発生
- 原因: LM Studio の sustained-load 劣化
- 結論: LM Studio 劣化が「実験結果」を汚していた

今回は「両 variant で同じ劣化パターンが見られるか」をチェックする

### 3.2 前半/後半スコアの算出方法

#### 方法 1: MongoDB から直接取得（精密版）

```bash
# SC-ON の session を確認
cd /Users/nrm176p/GitHub2/LLM/app/backend/eval
grep "_session_id" results/*-sc-on.json | head -1

# 出力: results/20260613-224523-sc-on.json:  "_session_id": "6a2182aa59e4931ddf9b3485",
SESSION_ON="6a2182aa59e4931ddf9b3485"

# SC-OFF の session を確認
grep "_session_id" results/*-sc-off.json | head -1
SESSION_OFF="6a2182aa59e4931ddf9b3486"
```

MongoDB から前半/後半を抽出：
```bash
docker compose exec mongo mongosh tanka_chat << EOF
// SC-ON
db.sessions.aggregate([
  { \$match: { _id: ObjectId("$SESSION_ON") } },
  { \$unwind: "\$messages" },
  { \$match: { "messages.type": "complete" } },
  { \$group: { 
      _id: null, 
      scores: { \$push: "\$messages.score" },
      count: { \$sum: 1 }
    } 
  }
])
EOF
```

#### 方法 2: Compare.sh の出力だけで判定（簡易版）

詳細な前半/後半分析がない場合、以下を確認：

```bash
# compare.sh 出力を再度見て、全体的なトレンドが安定しているか確認
./compare.sh sc-on sc-off | grep -E "(avg_final_score|plateau|max_refines)"
```

**簡易判定**:
- avg_final_score が両 arm で 50～100 の範囲なら通常 OK
- 0-50 の低スコア多発は後半の劣化を示唆

### 3.3 前半/後半スコア差の判定ルール

```
前半平均 - 後半平均 = D

|D| < 5   ⇒ OK (劣化なし)
5 ≤ |D| ≤ 10  ⇒ 軽度の劣化（ただし続行可）
|D| > 10  ⇒ NG (重度の劣化。この run は不採用。再実験推奨)
```

### 3.4 劣化チェック例

#### ケース A: SC-ON が劣化（NG）

```
SC-ON 前半平均: 87.0
SC-ON 後半平均: 62.5
差: 87 - 62.5 = 24.5 > 10  → NG

結論: この run は LM Studio 劣化の確実な証拠。
      Δ = +4.69 が有意でも、この run は採用不可。
      再実験推奨。
```

#### ケース B: 両 arm 共に安定

```
SC-ON 前半平均: 78.0, 後半平均: 76.5, 差: 1.5  → OK
SC-OFF 前半平均: 82.0, 後半平均: 81.0, 差: 1.0  → OK

結論: LM Studio 劣化の証拠なし。
      Δ = +4.69 の判定を信頼できる。
```

## Step 4: 最終判定テンプレート

### ケース 1: SC-ON が有意に有効 (Δ < -2.7, LM Studio OK)

```
【条件】
- |Δ| > 2.7
- Δ < 0 (sc-ON が高い)
- 前半/後半劣化チェック: OK (|差| < 10)

【判定】
✅ Self-critique は効果あり

【推奨アクション】
- Self-critique を保持
- TANKA_SELF_CRITIQUE=1 をデフォルトに保つ
- +1 LLM call のコストは正当化される

【根拠】
N=50 テーマでノイズ幅 ±2.7 を超える有意な改善が観測されました。
LM Studio 劣化の証拠もないため、信頼性が高い。
```

### ケース 2: SC-OFF が有意に優位 (Δ > 2.7, LM Studio OK)

```
【条件】
- |Δ| > 2.7
- Δ > 0 (sc-OFF が高い)
- 前半/後半劣化チェック: OK (|差| < 10)

【判定】
❌ Self-critique は有害

【推奨アクション】
- TANKA_SELF_CRITIQUE=0 に変更
- self-critique フェーズをスキップする
- コード上では条件分岐をそのまま保ちつつ、デフォルト値を反転

【考察】
Self-critique 指示が実は LLM の composition を悪化させているか、
または「自己点検を促す」というメタレベルの指示が、
LLM の focus を削ぐ可能性があります。
さらに詳細な分析（violation 種別の変化など）が有用です。
```

### ケース 3: 判定不能 (|Δ| ≤ 2.7)

```
【条件】
- |Δ| ≤ 2.7 (ノイズ幅以内)

【判定】
❓ 判定不能 / 有意差なし

【推奨アクション】
追加実験の選択肢：
1. Paired repeated measure: 各テーマで ON/OFF を複数回実行し分散を削減
2. より大規模なテーマセット (n=100+) で統計力を上げる
3. 異なるモデル (gemma など) で再測定し、モデル依存性を確認
4. Per-rule analysis: 特定の rule (kigo_unique など) だけ効果があるかを調査

【結論】
現状では「self-critique が効果を持つ」と主張することも、
「効果がない」と主張することも、統計的根拠が不足しています。
コストが +1 call で相応にオーバーヘッドが大きい場合、
保守性の観点から「オフに倒す」のも合理的です。
```

### ケース 4: 前半/後半に大逆転 (LM Studio 劣化)

```
【条件】
- |Δ| > 2.7 (一見有意に見える)
- 前半/後半劣化チェック: NG (|差| > 10)

【判定】
⚠️  この run は採用不可。LM Studio 劣化の確実な証拠

【推奨アクション】
1. 実験を再実行
2. 改善案:
   - 各 variant 間に 15-30 分以上の LM Studio アイドル時間を確保
   - eval.sh を background で実行し、その間に LM Studio を診断しない
   - 複数の eval.sh を並行実行しない（load を分散させない）
3. 再実験で同じ劣化パターンが見られたら、
   ホスト側の LM Studio リソース不足が疑われます

【参考】
CLAUDE.md §6.13: LM Studio sustained-load 劣化の記録
```

## FAQ: 判定の困難ケース

### Q1: 観測差が Δ = +2.6 （ノイズ幅ギリギリ）

```
|2.6| < 2.7?  YES

判定: ノイズ内
ただし、「有意差なし」ではなく「判定の境界上」であることに注意

推奨: 
- 0.1 点の小さな差で判定が変わる不安定性がある
- 複数 run の平均を取るか、詳細な劣化チェックで補強すること
```

### Q2: Δ = +5.0（有意）ただし前半/後半差が ±8（グレーゾーン）

```
|Δ| = 5.0 > 2.7  → YES, 有意
|差| = 8, threshold = 10  → グレーゾーン

判定: 採用可（ただしカテゴリ「軽度の劣化あり」）
推奨: 「この run は採用するが、LM Studio 劣化の軽度の影響の可能性あり」と報告
```

### Q3: Δ が一見大きいが、violation_frequency に異常が見られる

```
例: Δ = +7.0（有意に見える）
    ただし schema_invalid が SC-OFF で多発（10 vs 1）

判定: 有意ではあるが、「エラーの出やすい run」である可能性
推奨: 「スコア上では有意だが、エラー率の差が結果を歪めている。
       モデルのばらつきが大きい run。信頼性がやや低い」と注記
```

### Q4: 複数の runs を並行実施した場合、どの結果を採用?

```
推奨: 複数 run の平均を取る

例: 3 回実験した場合
  run-1: Δ = +2.0
  run-2: Δ = +4.5
  run-3: Δ = +1.2
  平均: Δ = +2.57

判定: 平均ですら ノイズ幅 ±2.7 に収まる → 判定不能

または: stdev = 1.6 を用いて信頼区間を算出
```
