作成日: 2026-06-12

実行対象: 短歌生成パイプラインの self-critique フェーズ

================================================================================

## 実験の目的

短歌生成パイプラインの Compose フェーズ直後に実行される「自己点検」(self-critique)
フェーズが、実際に品質向上に寄与しているか、数値的に測定する。

## 実験設計の要点

- 問い: self-critique フェーズの効果測定
- 対象: 50 テーマ × 2 arm (ON vs OFF) の比較
- 判定基準: ノイズ下限 ±2.7 点（n=50の 95% 信頼区間）
- 期間: 1 夜間実行（2-3.5 時間）
- 環境: LM Studio + llm-jp-4-8b-thinking (context 32768)

## 交絡対策

1. **LM Studio 劣化**: 各 variant 実行前に fresh reload
2. **失敗記憶の順序効果**: 各 variant 実行前に failures をリセット
3. **LM Studio 劣化の交絡検査**: 前半/後半スコア比較で、劣化が両 arm で対称かチェック

## 使用方法（ユーザー向け）

### 実験前 (1 日前)
1. README.md を一読
2. EXPERIMENT_DESIGN.md で実験設計を確認
3. ユーザーに以下を確認：
   - テーマセット (n=50)
   - 所要時間 (2-3.5 時間)
   - failures リセットへの同意

### 実験当日
1. CHECKLIST.md を印刷（紙持参推奨）
2. RUNBOOK.md に従い Step 0-8 を順序通り実行
3. CHECKLIST.md で進捗チェック

### 実験後（完了から 10 分以内）
1. JUDGMENT_CRITERIA.md で結果を解釈
2. 観測差とノイズ下限 (±2.7) を比較
3. 前半/後半の劣化パターンを確認
4. 判定を確定（採用/棄却/判定不能）
5. FINDINGS.md に結果を記録

### 変更が必要な場合
1. config.py / docker-compose.yml を修正
2. PR を作成し、数値と判定根拠を記載
3. Merge

## 判定基準（重要）

**ノイズ下限**: ±2.7 点 (n=50 テーマ)

判定フロー:

  観測差 Δ = avg_final_score(sc-ON) - avg_final_score(sc-OFF)

  |Δ| > 2.7?
    ├─ YES かつ Δ > 0:  sc-ON 有効 → 採用推奨
    ├─ YES かつ Δ < 0:  sc-OFF 優位 → 棄却推奨
    └─ NO:            ノイズ内 → 判定不能

  + 劣化チェック: 前半/後半スコアに異常がないか
                → 異常なら: 再測定

## トラブル時の対応

| 問題 | 対応 |
|---|---|
| eval timeout | 続行。nohup で背景実行。tail -f で監視 |
| health error | ./app/start.sh 再実行 |
| context exceeded | lms load ... --context-length 32768 で再初期化 |
| LM Studio slow | 別日に再実行 / モデル fresh reload |
| n が異なる | テーマファイルを統一 (eval_themes.json) |
| 劣化が大きい | 異常な run → 採用不可 → 再測定 |

詳細は各ドキュメント内のセクションを参照。

## 実験完了後の流れ

1. JUDGMENT_CRITERIA.md で判定を確定
   → 採用 / 棄却 / 判定不能 のいずれかを決定

2. 結果を app/backend/eval/FINDINGS.md に追記
   - テーマセット n=50
   - 観測差
   - 判定根拠
   - 交絡の有無

3. コード変更が必要な場合
   - config.py: SELF_CRITIQUE_ENABLED を修正
   - docker-compose.yml: TANKA_SELF_CRITIQUE のデフォルトを変更
   - PR を作成 (commit message に数値を記載)

4. 次の実験を検討
   - 判定不能の場合: n 拡張 or paired design で再測定
   - 発見があった場合: 他フェーズへの影響を調査

## 次のイテレーションへの提案

この実験で判定不能の場合、以下を検討：

1. **n=100 への拡張**
   - ノイズ下限を ±2.7 → ±1.9 に縮小
   - 時間: 4-6 時間 (現在の 2 倍)

2. **Paired design での再測定**
   - 各テーマで ON/OFF を交互に実行
   - per-theme の分散を削減
   - 時間: 4-8 時間（n がかさむ）

3. **モデル依存性の確認**
   - デフォルトモデルでは無効でも、
     大型 instruction-tuned model では有効の可能性
   - 別実験として設計

## 質問・問題解決

1. **実験設計に疑問がある**
   → EXPERIMENT_DESIGN.md の「5. 交絡対策」を確認
   → ユーザーに改めて相談

2. **実行中にエラーが出た**
   → RUNBOOK.md の「トラブルシューティング」を確認
   → 継続不可能なら一時停止して報告

3. **結果を解釈できない**
   → JUDGMENT_CRITERIA.md の「判定フロー」セクション
   → ±2.7 との比較チャートで判定

4. **再実験が必要**
   → JUDGMENT_CRITERIA.md の「パターン 3: 判定不能」を参照
   → 次の実験設計（n 拡張 or paired）を検討
