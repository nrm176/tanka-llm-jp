## 0. 事前登録した判定基準 (解釈より先に固定)

- 比較単位は **16 お題 × 単一 run 同士** → スキルのノイズ下限表より、偶然生じうる平均差は
  **±4.8 (2SE)**。これを超えない平均スコア差では採否を結論しない
- 補助的に paired (お題ごと差分) の 2SE も実測し、より厳しい方を尊重する
- 「差はノイズ内 = 判定不能」も正当な結論として報告する

## 3. 判定: ノイズ下限との照合

- 観測差 **+4.69 < 事前登録ノイズ下限 ±4.8** → 平均スコア差は統計的に区別不能
- paired 分析 (お題ごと差分、n=16) ではさらに明確:
  - mean = +4.69, **sd = 26.13**, 2SE = **±13.1** → 観測差はノイズ幅の 1/3 程度
  - 符号: **ON 優位 9 お題 / OFF 優位 7 お題** — 方向の一貫性なし

## 4. 交絡チェック (前半/後半分割) — 決定的

| run | 前半 8 | 後半 8 | 落差 |
|---|---|---|---|
| sc-on | 88.1 | **62.0** | −26.1 (クレーター) |
| sc-off | 83.2 | 76.2 | −7.0 |

- **半分割で結論の符号が反転する**: 前半のみなら ON 優位 (+4.9)、後半のみなら OFF 優位 (+14.2)。
  スキル Step 4-3 の規定により、この run ペアは採否判断に使えない
- OFF の見かけの勝ちは後半 3 お題 (紅葉の散る山道 +59 / 炬燵で蜜柑 +55 / 冬の寂寥 +47) に集中。
  これらは sc-on run が 35/42/42 と沈んだ箇所で、self-critique の害ではなく **sc-on run 後半の
  LM Studio sustained-load 劣化** (CLAUDE.md §6.13) と整合
- 傍証 (wall-clock): セッション時刻より sc-on は 16 お題に **約 21.5 時間** (≈80 分/お題)、
  sc-off は **約 2 時間 20 分** (≈9 分/お題)。sc-on run が深刻な劣化下で走っていたことを強く示す

## 5. 半分割で符号が反転しない唯一のシグナル: 初回品質

self-critique の設計目的 (初稿の自己点検) に直結する指標は、むしろ ON 優位で一貫:

| 指標 | sc-ON | sc-OFF | 備考 |
|---|---|---|---|
| 初回 attempt 平均スコア (全体) | 53.9 | 40.0 | +13.9 (ON) |
| 同・前半 8 | 63.1 | 49.2 | +13.9 (ON) — 両半で同方向・同幅 |
| 同・後半 8 | 44.8 | 30.8 | +14.0 (ON) |
| 初回合格 | 6/16 | 1/16 | Fisher exact p = 0.083 → 有意水準 5% では未達 |

統計的に確定はできない (n=16・単一 run・blocked) が、「self-critique は探索の開始点を引き上げる」
という設計仮説と方向が一致し、**切る方向を支持する証拠はゼロ**である。

## 6. コストの整理

- self-critique は **生成あたり 1 回だけ** 実行 (compose 直後・refine ループ外、`tanka.py:216`)
  → コスト = +1 LLM call/生成
- 本サンプルでは avg_attempts が ON 3.56 / OFF 3.94 で、+1 call は refine 減で部分相殺
  (ただし attempt 数差自体もノイズ域)

## 7. 結論

**self-critique フェーズは切るべきでない (現状維持 = 既定 ON のまま)。**

1. 平均スコア差 +4.69 (OFF) は事前登録ノイズ下限 ±4.8 未満、paired 2SE ±13.1 に対しても
   遥かに小さく、**統計的に「効果なし」とも「OFF 優位」とも言えない**
2. 前半/後半で結論の符号が反転する交絡 (sc-on run の LM Studio 劣化、wall-clock 9 倍差で裏付け)
   があり、この run ペアは**そもそも採否判断の根拠に使えない**
3. 切替えの挙証責任は変更側にある。「OFF にして良い」ことを示す有意な証拠がない以上、
   既定 (ON) を維持する。さらに、半分割で頑健だった唯一のシグナル (初回品質 +14 点、初回合格 6/16
   vs 1/16) は ON 優位方向であり、切ると初稿品質を失うリスクの方が示唆される

### もし +1 call/生成 のコスト削減が本当に必要なら (再測定の設計)

- **paired/interleaved**: お題ごとに ON/OFF を交互実行 (両者が同じ LM Studio 状態を経験する)
- variant ごとにモデルの fresh reload、run 間にインターバル
- お題ファイルは `app/backend/eval/` 配下に置く (`/tmp` 禁止)
- 判定基準は事前登録: paired n=16 なら今回実測の paired sd≈26 を使い 2SE ≈ ±13 が目安
  (それ以下の差なら「コスト最適化としても判定不能」で打ち切る)
