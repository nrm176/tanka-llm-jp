What it is

これは何か

ブラウザのチャット画面からお題を投げると、バックエンドが 構想 (Plan) → 作歌 (Compose) → 検証 (Validate) → 改稿 (Refine) のパイプラインを走らせ、途中経過を SSE で流し、合格した短歌をセッション履歴に保存する。モデルは LM Studio 上のローカル 8B (llm-jp-4-8b-thinking) で、認証なし・localhost 前提の個人向け実験環境。

賭けは一つ。モデルを賢くしない。ファインチューニングも大型化もせず、出口に決定的な検証器を置き、モデルには「速くドラフトを出し、指摘に応じて詠み直す」ことだけを求める。8B は指示追従が弱く、構想で決めた季節を作歌で勝手に変える。それを願いではなくルールで矯正する。

JSON 強制

出力は型で受ける

短歌は自由文ではなく JSON (季語・季節・五句の本文と読み・情景・心情)。Pydantic で検証でき、ルールが書ける。

決定的検証器

機械が採点する

拍数・季語の唯一性・季違い・構想との整合を副作用なしの純関数で判定。100 点から減点し、80 以上で合格。

best-of-N 改稿

指摘を返して詠み直す

不合格なら critique を user メッセージとして返す。固定回数ではなく plateau で止め、全試行の最高点を採用。

Topology

システム構成

4 つのコンテナと、Docker の外で動く LM Studio。LLM 呼び出しは HTTP リクエストの寿命から切り離されている。

切り離しの仕組み

POST /api/tanka は task_id だけを即座に返し、生成本体は asyncio.create_task で背景実行される。クライアントは GET /api/tasks/{id}/stream を購読するが、購読を切っても背景タスクは完走する。イベントは Redis Streams に積まれるため、再接続時は XREAD … 0 で頭から再生できる。Pub/Sub ではなく Streams を選んだのはこの replay のため。

セッション切替で SSE だけを abort し、完了時は MongoDB に永続化。graceful shutdown は lifespan と stop_grace_period: 30s で partial save の時間を確保している。

Pipeline

生成の流れ

Plan で季語と季節を決め、Compose で JSON を書かせ、Validate で採点し、不合格なら Refine へ戻す。各段を選ぶと、何を送り何が返るかを示す。

REFINE → VALIDATE → STOP? を、合格・plateau・上限のいずれかまで繰り返す

messages 配列の形 — system は静的、状態は user に流す

LLM へ渡す配列は、役割定義の system プロンプト (定数、全 attempt で不変) と、動的な状態を積んだ user メッセージで構成される。critique も教訓も構想の制約も、すべて user 側に埋め込む。refine で送るのは 固定ベース + 直近 1 ラウンドだけで、attempt が増えても context は伸びない。

Validator

検証器 — 朱を入れるのは機械

validator.py は副作用のない純関数の集合で、DB も Redis も知らない。LLM の生出力から JSON を剥がして Pydantic Tanka にし、ルール関数を順に回して違反を集め、100 − Σ重み を score とする。読みはモデルの申告を信用せず、本文の漢字から pykakasi と古語読み辞書 (kogo_yomi.json) で独立に算出する。

ルールは 3 層。Tanka だけで判定できる 8 ルールは RULES リストに並び、関数を 1 つ書いて append すれば増える。構想との整合 2 ルールは Plan の値が要るため evaluate() の引数経由で注入。お題との整合 3 ルールは theme を受けて時刻語・主題語の矛盾と欠如を見る。全ルールに LESSONS の教訓文があることをテストが保証する。

減点シミュレータ

違反を選ぶと score がどう落ちるかを見る。重みは加法。critical 1 つで 80 を割るものがある一方、minor は 6 つ重ねても合格できる。

100 / 100
合格
score = max(0, 100 − Σ weight)  ·  passed = score ≥ 80
減点なし

停止条件

  • 合格: score ≥ 80 で即終了。その attempt を採用
  • plateau: 直近 3 試行で best が更新されなければ打ち切り。過去最高の案を採用
  • hard cap: attempt ≥ 50 (安全網、通常踏まない)
  • llm_error: context 超過やタイムアウトなら best-so-far で打ち切り (zero-output を防ぐ)

不合格の attempt は毎回 failures に記録され、次回以降の生成で教訓として注入される。合格しなかった歌もベストを返すが、UI では「規定未達」バッジが付く。

Feedback design

フィードバック設計 — コードを読むと誤解する 3 点

引き継ぎで最初に読むべき feedback-architecture.md の要点。表面的に読むと逆に理解してしまう箇所がある。

よくある誤解実態
validator は出力を通すか落とすか判定する checker数値・違反詳細・自然言語 critique・教訓フレーズを生成するフィードバック信号発生器。改稿の方向はここで決まる
失敗記憶は「悪い出力 + 修正版」の few-shot として LLM に見せている見せていない。違反を LESSONS で 1 行の教訓に圧縮し、user メッセージ末尾に箇条書きで埋め込む。raw の悪例は 8B が「お手本」と誤認するため
validator の結果は system プロンプトに反映されるされない。system は module-level 定数の参照が 3 箇所あるだけで一度も書き換えない。状態は user/assistant の交互で表現する

なぜ system を触らないか

「あなたは歌人」と「前回 65 点だった」を混ぜると役割認識が揺れる。system を毎回書き換えると refine 履歴と二重に状態が累積して context を圧迫する。refine は本質的に「前の出力 + 指摘 → 次の出力」の対話であり、critique は user 発話として自然。実装も system は定数参照、user は append のみで済む。

長期失敗記憶の実体と限界

compose 直前に、同じモデル・同じ季の直近 3 件の失敗を failures から引き、最重要違反のルール名を教訓文に変換して注入する。モデル別に分けるのは、別モデルの癖で書かれた教訓が汚染するのを防ぐため。UI の「教訓」ブロックも注入と同じ関数から生成するので、見えているものと送ったものが一致する。

効果は正直に言って限定的。教訓は system の作法とほぼ同じ内容で新情報が少なく、修正例の対比も無い。実際の品質保証は validator のルール強制と refine ループが担い、長期記憶は補助輪に留まる。強化するなら「失敗 → 修正版」ペアの本物の few-shot 化や、悪例の断片併記が候補。

context を attempt 数から独立させる

かつては refine 履歴を積み上げ続け、attempt が増えると "Context size has been exceeded" で出力ゼロになった。いまは compose の固定ベースに直近 1 ラウンド (assistant の直近出力 + user の最新 critique) だけを足す。critique が毎回問題点を伝えるので過去全部は要らない。self-critique も同じ形。

Case study

春アトラクター — 迷うと桜に落ちる

お題「夏の夕暮れ」。構想は正しく 夏 / 蛍 を選んだのに、最終出力は 春 / 花 の「花が散る」歌になり、47 点の不合格作が「完成」として採用された。結句「自然の理かな」は、compose プロンプト先頭の few-shot #1 (散る桜 / 春 / 花、emotion「自然の理への諦観」) からの直接コピーだった。

単発ではなかった。横断 52 件で plan の季と出力の季を突き合わせると、誤りは 100% 春への一方通行。夏・秋・冬へ横滑りした例は 0 件。

plan の季 ＼ 出力の季春夏秋冬正答率
春10···10/10 = 100%
夏810··10/18 = 56%
秋4·6·6/11 = 55%
冬2··66/8 = 75%
∅ (抽出失敗)5···0/5 = 0%

非春 plan → 春: 14/37 (37%)。春 plan は一度も出ていかず、抽出に失敗した 5 件は全部春へ。写し元を指紋で当たると few-shot #1 が 4 件、#2〜#4 は 0 件。「季節の合う例を写す」のではなく「先頭の最も鮮烈な例に固着する」。

対策: 動的 few-shot

それまでの修正 (整合ルールの追加、plan の JSON 抽出) は全部「検出」側で、磁石そのものを断っていなかった。対策は compose に見せる few-shot を plan の季に一致する 1 ペアだけにし、他季 (特に春) の例を隠すこと。同一 plan・同一制約で few-shot の OFF/ON だけを切り替える統制実験 (非春 4 題 × 3 反復、OFF/ON 隣接) を行った。

OFF · 四季全部を見せる (従来)
8 / 12
春へ転落 67%。夏の夕暮れ 3/3、紅葉の散る山道 2/3、名月を仰ぐ宵 2/3、冬の寂寥 1/3
ON · お題の季の 1 ペアだけ
0 / 12
春へ転落 0%。parse 失敗も増えず (24/24 成功)。「四季を揃えないと壊れる」という旧前提は否定された

TANKA_DYNAMIC_FEWSHOT=1 が既定。新年は専用ペアを別に持つ (新春・初春が春に隣接し、四季フォールバックに落ちると磁石が復活するため)。

Measurement

測定で分かったこと

固定お題セットを機械的に回す評価ハーネス (eval.sh / eval-repeat.sh / eval-paired.sh / compare.sh) を作った途端、主観では見えなかったことが複数見えた。

1. これは反復改善ではなく best-of-N サンプリング

refine は前の歌を編集するのではなく、critique を見てゼロから別の歌を生成する。最終結果は全試行の最高点。同一お題「散りゆく桜」を 6 回生成すると、改稿回数とスコアは無相関だった。

比較単位平均の標準誤差偶然生じうる差 (2SE)
単一お題・単一 run±9.6±19
8 お題の平均±3.4±6.8
50 お題の平均±1.4±2.7

8 お題 eval で ±6.8 以内の差はノイズ。以前「全項目改善 +2.86」と表示された比較は、このノイズ幅以下の運の差だったと確定した。以後、パイプライン変更の採否はノイズ幅を超える差だけで判断する。

2. 素の実力と最終品質の順位が反転する

同じ 12 題で 3 モデルを統制比較した。初稿で合格する率 (素の実力) は llm-jp が圧倒的だが、best-of-N の最終平均は最下位。一発の実力が最低の gpt-oss-20b が、refine に素直に応じ暴走しないため最高の平均に磨き上がる。

3. self-critique の効果は結論不能 → paired 設計へ

compose 後の自己点検フェーズ (+1 LLM call) を 16 題 × ON/OFF の blocked A/B で測ったところ、差 +4.69 はノイズ下限 ±4.8 の内側。しかも前半/後半に割ると ON 側の後半だけ LM Studio の持続負荷劣化で 62.0 点に沈み、前半だけなら符号が逆だった。環境劣化が交絡する不安定なハードでは blocked A/B は信用できない。

そこで現在、お題ごとに ON/OFF を ABBA で交互に走らせ、両 arm が同じ LM Studio 状態を経験する paired ハーネス (eval-paired.sh、per-request の self_critique 上書き、中断再開、事前登録の判定基準) を整備中。存続判断はその結果まで保留。

4. 測定が見つけた本物のバグ

手動テストでは踏まなかった 2 件が、固定お題を機械的に回して初めて顕在化した。refine 履歴の無限増加による context 超過と、timeout の無いストリームが stuck connection で 14 分黙ってブロックする問題。どちらも修正済みで、測定基盤の費用対効果の証拠になった。

Principle

設計原則 — ツールに検証させ、モデルには反復させよ

外部に決定的な検証器と refine ループを持つ設計では、モデル内部の自己検証 (thinking) は二重の無駄になる。validator が決定的・正確にやる仕事を、モデルが確率的・不正確に再実行し、捨てられる検証にトークンと時間を払う。さらに「5-7-5-7-7 を数えろ」のような制約は thinking モデルに拍数の再計算ループを誘発し、モデルは自分の出力文字列を観測できないため収束せず、予算を使い切って </think> に到達しないまま空出力になる。この暴走は 8B でも 30B でも再現した。モデル非依存の病理で、規模では解決しない。

検証器とモデル内 thinking は補完財ではなく代替財。両方に金を払ってはいけない。

系: モデル選定

  • ベンチマークの素の実力で選ばない。refine 応答性 × 壊滅事故の無さで選ぶ
  • 理想の型は非-thinking か、think を確実に閉じる thinking。分離 reasoning で閉じない型は構造的に不適合で、導入前のプローブで弾く
  • 規模・世代・日本語特化は二次的

適用範囲の歯止め

原則は「検証器がカバーする次元」でだけ成立する。拍数・季語・スキーマは機械判定できるので速い無事故モデルで足りる。詩情・余韻・自然さは validator が採点できず、素のモデル品質がそのまま出る。ここでは llm-jp の日本語特化 (名歌 90〜100 の産出力) が依然最強で、refine では埋められない。だから単一モデルに収束せず、llm-jp (質の天井) と閉じる系 (無事故・速度) をセッションごとに使い分けるのが現在の解。

領域外部検証器原則の含意
コード生成コンパイラ · 型検査 · テスト速く書いてテストで直させる > 遅い自己検証モデル
構造化抽出スキーマ validatornon-thinking + リトライで十分なことが多い
短歌 (本件)拍数 · 季語 validator実証済み。素の実力順位と最終品質順位が反転した
