問題設定

短歌は、制約の塊である

  • 拍数 5-7-5-7-7拗音は1拍に数えない、促音・撥音・長音は各1拍 …機械的だが厳密
  • 季語は ちょうど1つなし ✗ / 2回 ✗ / 別の季の季語との同居（季重なり） ✗
  • お題・構想との 整合「夏の夕暮れ」と頼んだのに春の歌が来たら破綻

これを ローカルの 8B モデルにやらせたい。ところが 8B は指示追従が弱い。
「絶対に季節を変えるな」と書いても──変える。

素朴な策は負ける

「賢くする」方向は、行き止まりだった

  • プロンプトで祈る【重要・必須】と強調しても、8B は従わない。願いは制約にならない
  • thinking に頼る「5-7-5-7-7 を数えろ」が思考の暴走を誘発。モデルは自分の出力文字列を観測できないため、数え直すたびに違う答えが出て収束しない
  • 大きいモデルに替える30B でも同じ病理で暴走した（モデル非依存）。content が空のまま全試行失敗という形で現れる

では、モデルを賢くするのをやめたらどうなるか。

発想の転換

検証器は "checker" ではない

pass/fail を返すだけなら checker。この validator は 3 つの顔 を持つ。

① 採点者

ルール × 重みで減点採点。season_matches_plan −30 / kigo_matches_plan −20 / kigo_present −25 … 構想との整合を「願い」でなく点数で強制する

② 批評家

違反を「なぜダメか・どう直すか」の critique 文に整形し、refine プロンプトへ注入。モデルは具体的な指摘に対してだけ直せばよい

③ 教師

失敗を DB に記録し、教訓 (LESSONS) として次回以降の生成に注入。悪い例を "お手本" と誤認する 8B への安全策として、生例でなく教訓フレーズに圧縮（効果は補助輪 ── 品質保証の主役は ①②）

発見 ① ── 真因

磁石は、プロンプト先頭の例だった

few-shot は四季 4 例を見せていた。どの例が「写された」かを指紋照合すると──

few-shot 例写された件数
#1 散る桜（春/花）4 件
#2 夏の夜（夏）0
#3 秋風（秋）0
#4 冬（冬）0

動かぬ証拠

事件の歌の結句「自然の理かな」は、例 #1 の emotion「自然の理への諦観」からの直接コピー。情景・心情も #1 のほぼ言い換えだった。

「季節の合う例を参考にする」のではなく、先頭の最も鮮烈な例そのものへ collapse していた。
おまけ: RAG が注入した参考歌の冒頭も「春過ぎて」（冒頭の歌）── 春の磁石が目前に 2 つ並んで見えた。
ただし後の追試で、主磁石（few-shot #1）を断てば RAG 単独ではドリフトしないことも確認済み（9/9 注入で転落 0）。

発見 ① ── 対策と実証

磁石を隠す ── 動的 few-shot

構想の季に一致する例を 1 ペアだけ 見せ、他季（特に春）の磁石をプロンプトから消す。
統制実験（同一構想・few-shot 切替のみ・非春 4 テーマ × 3 反復 × OFF/ON = 24 試行）:

67%OFF: 四季全部見せる（従来）
春へ転落 8/12 → 0%ON: 動的 few-shot
春へ転落 0/12

「夏の夕暮れ」は OFF 3/3 → ON 0/3。1 ペア提示でも JSON 破綻は増えず、
「四季を揃えて見せないと壊れる」という当初の思い込みはデータで否定された。

発見 ② ── 序

次の問い ──「どのモデルが一番いいのか」

パイプラインが固まったので、モデルを差し替えて統制 eval（同一お題 12 題）で比較した。

llm-jp-4-8b-thinking（8B）

日本語特化の thinking モデル。一発で良い歌を出す力は最強クラス

gemma-3-27b（27B）

非 thinking の汎用モデル。3 倍のサイズ

gpt-oss-20b（20B）

thinking を確実に閉じるタイプ。日本語短歌の一発力は…正直弱い

普通に考えれば「一発の実力が高いモデル」が勝つはず。──ところが。

  • 一発の実力 最下位 (8%) の gpt-oss が、refine ループを経ると 最高 avg に磨き上がる（質の天井は依然 llm-jp）
  • 一発の実力 最強 (75%) の llm-jp は、thinking 暴走による zero 出力 17% が足を引く
  • 外部検証ループが「素の弱さ」を吸収し、応答性 × 無事故性 を品質に翻訳した
発見 ② ── なぜそうなるか

検証器と thinking は、代替財である

冗長

validator が決定的・正確にやる仕事を、モデルが確率的・不正確に再実行している

浪費

どうせ捨てられる自己検証に、トークンと context と待ち時間を払っている

自滅

拍数のような「文字列を見ないと検証できない制約」で thinking は収束せず暴走。</think> に到達しないまま予算が尽き、出力が空になる

両方に金を払ってはいけない。

検証責任が機械に割り当てられているなら、モデル内の自己検証は二重の無駄であり、制約が重いときは事故の発生源になる。

設計原則

検証器を持つ側が、
モデルの役割を決める。

  • 検証は機械に。モデルには「速く出して、指摘に応じて直す」ことだけを求めるLet the tool verify; let the model iterate.
  • モデル選定は「ベンチの素の実力」でなく refine 応答性 × 無事故性 で非 thinking か、確実に閉じる thinking を選ぶ
  • ただし効くのは検証器が見える次元だけ拍数・季語は機械が守れる。詩情・余韻は採点できず、素のモデル品質がそのまま出る
持ち帰り

賢さは、外付けできる

  • 小さいローカルモデル ＋ 決定的な検証器 ＋ critique/教訓のループ= 「モデルを大きくする」以外の勝ち筋
  • few-shot は 磁石 になる見せる例は「全部」でなく「選んで」。先頭の鮮烈な例は吸着点になりうる
  • 設計を変えると、モデルの選び方まで変わる一発 8% のモデルが最終 1 位になる世界がある

コード生成ならコンパイラとテスト、構造化抽出ならスキーマ validator ──
決定的なチェッカーをループに持てる場なら、同じ設計がそのまま効く。

付録 B ── 罠コレクション

ローカル LLM 運用で実際に踏んだ罠

  • サイレントハング 14 分stuck connection で例外なく無限ブロック。チャンク間 read timeout (120s) で fail-clean に
  • refine 履歴の context 爆発全試行を会話履歴に積むと "Context size exceeded" で zero 出力。固定ベース + 直近 1 ラウンドに
  • JIT ロードは context 8192 で載るthinking モデルは即死。生成前に 32768 で明示ロード必須
  • IME の Enter で誤送信日本語 UI では変換確定 Enter が送信を暴発させる。送信は Cmd/Ctrl+Enter のみに
