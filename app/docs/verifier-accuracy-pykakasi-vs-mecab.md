# 検証器の精度調査: pykakasi の拍数誤読と MeCab(UniDic)移行の実利

> 区分: 調査記録 (実測ベース。採用は eval で確定させること)
> 日付: 2026-07-10
> 関連: `reading.py` / `validator.py` (`_rule_mora_count`) / CLAUDE.md §6.3, §7 /
> [design-principle-verifier-in-the-loop.md](./design-principle-verifier-in-the-loop.md) §5

## 0. 背景 — なぜ「検証器の精度」を調べるのか

設計原則 (design-principle §5) に「**検証器を強く・信頼できるものにするほど、モデルには考えさせなくてよい**」
とある。検証器を強くする最も直接的なレバーは、拍数判定の心臓部 `reading.py` の**読み精度**である。
現状は pykakasi (現代漢字辞書ベース) を使い、CLAUDE.md §6.3 のとおり**古典固有読みを誤る**
既知の弱点がある (例: 「日」を「ひ」と読めない)。

そこで本書は「**MeCab + UniDic に移行すれば拍数精度はどれだけ上がるか**」を、
主観でなく**実測**した記録である。結論を先に言うと **移行はクリーンな勝利ではなかった**。

## 1. 現状設計の再確認 — validator は既に pykakasi 誤読を hedge している

`_rule_mora_count` は pykakasi の誤読に対して**3 段の安全網**を持つ (これ自体が優れた設計):

| 状況 | ルール | 重み |
|---|---|---|
| pykakasi と食い違うが**モデル提供読み**は正しい (古典読み疑い) | `mora_count_disputed` | -3 (minor) |
| 1 拍だけずれ (字余り/字足らず) | `mora_count_off_by_one` | -3 (minor) |
| 2 拍以上ずれ (本物の違反) | `mora_count` | -10 (critical) |

**要点**: 拍数を漢字本体から独立に算出しつつ、pykakasi が外しても**モデルが JSON で返した `reading`
フィールドと突き合わせて minor に降格**する。つまり「辞書が全知でなくてもよい」設計。
この hedge の存在が、以下の「移行の実利」評価を左右する。

## 2. 実測 A/B — pykakasi vs fugashi + unidic-lite (MeCab)

### 2.1 方法

- data コーパス (`classical_tanka.json`) は gitignore 済みで未クローンのため、**有名な公有の古典語・
  現代ヘテロニム n=18** を高信頼の参照読みつきで自作 (百人一首・芭蕉句・菅原道真歌など)。
- `reading.py` と同一の拍数ロジック (拗音吸収・記号除去) で、両エンジンの読みから拍数を算出し、
  参照拍数との一致率を比較。統制として現代語も混ぜ、MeCab の退行も測る。
- 再現コマンド (プロジェクトに依存追加せず isolated env で):
  ```
  uv run --with fugashi --with unidic-lite --with pykakasi python <probe>
  ```

### 2.2 結果 (n=18)

| | 拍数一致率 | 内訳 |
|---|---|---|
| **pykakasi** (現行) | **11/18 = 61%** | 現代ヘテロニム・古典読みで失点 |
| **UniDic** (fugashi+unidic-lite) | **13/18 = 72%** | 形態素解析で文脈読みを改善 |

- **UniDic が救済 (pyk✗→uni✓): 4 件** — 今日→きょう(pykは こんにち)、行方→ゆくえ(なめがた)、
  庵→いお(いおり)、夕月夜(読み違いだが拍は一致)
- **UniDic が退行 (pyk✓→uni✗): 2 件** — **海人→かいにん**(pykは あま で正)、
  **露→ろ**(pykは つゆ で正)。**露は短歌の最頻出語のひとつ**で、この退行は痛い
- **両者とも失敗 (真の文語読み): 3 件** — 東風=こち(菅公歌)、生ふる=おう、紅葉=もみじ/こうよう(本質的に曖昧)。
  **現代辞書ベースの形態素解析では原理的に解けない**

### 2.3 副次的発見: 拍数え自体が本質的に難しい

本調査の準備中、**筆者(人間 + LLM)が参照拍数を 18 件中 5 件も数え間違えた**
(例: 「かぜがふく」を 4 と誤記、正は 5)。これは §6.3 の教訓 —
「拍数は専用ツールでも人間でも間違える曖昧なタスク」— を皮肉にも裏づける。
**だからこそ決定的検証器を機械に置く価値がある**が、同時に **その機械も完璧ではない**ことを意味する。

## 3. 解釈 — なぜ「クリーンな勝利」ではないのか

1. **正味 +11pp だが混在**: MeCab は 4 救済・2 退行で、単純な上位互換ではない。特に **露/海人のような
   詩歌頻出の単独語で退行**する (UniDic の既定は文語より字音・語彙形を優先しがち)。
2. **一番効かせたい文語読みが未解決**: 東風=こち、生ふ=おう 等、短歌が実際に使う古語は
   現代 UniDic の守備範囲外。移行しても「両者失敗」の 3 件は残る。
3. **この n=18 は意図的に難問**: 統制の現代語はどちらも ~100%。実際のモデル出力は大半が平易な現代語で、
   さらに §1 の hedge (モデル提供読みで minor 降格) が既に効く。→ **実運用での正味改善は 11pp より小さい**。
4. **コストが重い**: fugashi (C 拡張) + 辞書。unidic-lite でも ~50MB、full UniDic は ~700MB。
   Docker イメージ肥大 + ビルド複雑化。§7 の「依存追加なし」哲学に反する。

## 4. 提案 — 移行より安い勝ち筋(優先順)

全面 MeCab 移行を第一手にしない。ROI 順に:

1. **【推奨・最安】ハンドキュレート古語読み override 辞書** (`kigo.json` と同じ方式、依存ゼロ)
   短歌頻出の古語 (庵=いお, 東風=こち, 五月雨=さみだれ, 時雨=しぐれ, 露=つゆ, 衣手=ころもで …
   数十〜百語) を `data/koga_yomi.json` に手で持ち、`reading.py` で **pykakasi の前段**に適用。
   §7 の哲学 (ハンドキュレート JSON・依存追加なし) に完全合致し、**両者失敗の 3 件をピンポイントで潰せる**。
2. **モデル提供 `reading` をもっと信頼する** — モデルは自分の**意図した読み**を知っている
   (辞書は漢字から復元できない)。現状は disputed 降格にしか使っていないが、
   モデル reading が妥当なら拍数の第一根拠に格上げする余地。ただし §6.16 系の空出力リスクと要両睨み。
3. **MeCab は "後で測って効けば" の候補に降格** — 上記 1/2 を入れた上で、実 eval 出力に対して
   fugashi+unidic-lite の A/B を回し、**露/海人の退行を超える正味改善が数値で出たときのみ**採用検討。
   採用時は unidic-lite (軽) で足りるか full UniDic が要るかも要測定。

## 5. エビデンス状況

| 項目 | 層 | 状況 |
|---|---|---|
| pykakasi/UniDic の拍数一致率 (n=18 自作難問セット) | C (方向性) | **実測済み** (61% vs 72%)。定量採否の根拠にはしない |
| 実モデル出力での正味改善 | — | **未測定**。§1 の hedge 込みで測る必要 |
| override 辞書の効果 | — | **未実装・未測定**。§4-1 が最有力の次アクション |

**結論**: 「検証器を強くする」方向性は正しいが、**その手段は MeCab 全面移行ではなく、
まず依存ゼロの古語読み override 辞書**。MeCab は頻出語で退行しうるため、実 eval で正味プラスを
確認できてからにする。数値は本書 §2、再現は `uv run --with fugashi --with unidic-lite ...`。
