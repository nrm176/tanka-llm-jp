# thinking 暴走対策 (#22) と eval 測定の顛末

> 期間: 2026-06-10 〜 06-11
> 関連: issue [#22](https://github.com/nrm176/tanka-llm-jp/issues/22) / PR [#23](https://github.com/nrm176/tanka-llm-jp/pull/23)、
> 併走した issue [#11](https://github.com/nrm176/tanka-llm-jp/issues/11) / PR [#13](https://github.com/nrm176/tanka-llm-jp/pull/13) の A/B 確定も本ドキュメントに含む

---

## TL;DR

llm-jp-4-8b-thinking の実思考トレースを精査し、**自己検証の暴走**（拍数の再計算ループ・存在しない空白の検証ループ）が
context 圧迫 (§6.10) とテーマあたり 4〜7 分の latency の主因であることを特定した。
対策として completion token 上限 (`TANKA_MAX_COMPLETION_TOKENS`) + prompt への自己検証抑止文言を実装。

A/B 測定の結果、**たたき台の 4096 は「もっともらしいが有害」**（合格率 -17pt、plateau 率 2 倍、所要時間は不変）と判明し不採用。
既定値を **8192 に修正し「latency 最適化」ではなく「真の暴走と context 超過だけを止める安全弁」として採用**した。

測定自体が 5 つの環境障害（JIT ロード罠・ハーネスのポーリング競合・停止漏れによるキュー二重実行・
バックエンドへの外部 SIGTERM・ホストの熱緊急スリープ）に阻まれ、それぞれの原因と恒久対策も本書に記録する。

---

## 1. 発端: 思考トレースの病理 (原因)

ユーザー提供の compose 思考トレース（31k 文字超）を精査した結果:

| # | 病理 | 具体例 |
|---|---|---|
| 1 | **ルールの暗唱はできるが適用できない** | 冒頭で「他の季語を入れるな」と自戒した直後、prompt が名指しで禁じている「夕立」(夏の辞書季語) を 1 句目に採用 |
| 2 | **表層文字列に接地できない** | 同一文字列の拍数が数え直すたびに 7→8→5 と変動。存在しない拍を幻視。拗音 (きょ) の扱いも 1 拍/2 拍で揺れる |
| 3 | **読みの捏造** | 胸=きょ (正: むね)、布=ぶ (正: ぬの) — 拍数を合わせるために読みを発明。「reading は自己申告」という構造を見抜く発言まで |
| 4 | **自己検証の無限ループ** | トレースの約 4 割が「な の前に空白がある気がする」の検証ループ。"I'm going insane" と自覚しつつ脱出不能。根因は #3 の誤読 1 つのカスケード |
| 5 | **prompt の明示指示を無視** | 「拍数の試行錯誤に時間を割くな」→ 9 割が拍数試行錯誤。「思考も日本語で」→ ほぼ全編英語 (romaji 経由の拍数計算が誤りを増幅) |

**根本診断**: 検証器が無いのではなく、検証器 (プログラム側採点) を信用できない。
接地できないモデルの自己検証は非決定的な再計算を繰り返して収束せず、context を燃やすだけ。
トレース末尾は文中切断 = 出力/context 上限到達の現場で、これが §6.10 (context 超過) と
高負荷時の連鎖失敗の実体だった。

## 2. 対策 (#22 → PR #23)

1. **completion token 上限**: `llm.stream_completion(..., max_tokens=)` を追加し、
   tanka パイプライン全フェーズ (plan/compose/self_critique/refine) に
   `config.MAX_COMPLETION_TOKENS` (env `TANKA_MAX_COMPLETION_TOKENS`、0 で無効) を適用。
   - **fail-clean 設計**: 打ち切りは `finish_reason=length` の正常終了 → harmony final マーカーが
     出ない → `schema_invalid` (score 0) → 既存の refine ループ / best-so-far フォールバックが回収。
     新規エラー処理ゼロ。強制打ち切りスモーク (cap=300) で例外ゼロ完走を実証済み
2. **prompt への抑止文言**: 「reading に空白・改行・句読点を含めない。
   **文字列の見た目の自己検証は不要** — 照合はプログラム側で機械的に行う」(病理 #4 のトリガー除去狙い)

## 3. 測定を阻んだ障害たち (原因 → 解決)

eval A/B が完走するまでに踏んだ環境障害。**すべて再発しうる**ので恒久対策とセットで記録する。

| # | 障害 | 原因 | 解決 |
|---|---|---|---|
| 1 | 全コールが "Context size has been exceeded" | LM Studio の **JIT ロード既定** (context **8192** + TTL 1h)。thinking の思考量が 8k を即超過 | `lms load llm-jp-4-8b-thinking --context-length 32768` の**明示ロード**。eval 前の必須手順 |
| 2 | テーマが並走して計測不能 | eval.sh の完了待ちが「タスクの fast-fail」も「ポーリングの一時失敗」も完了扱い → 次テーマを投入 | 完了判定を **null 2 連続観測**に変更 + 取得失敗はリトライ + テーマ間 60s クールダウン |
| 3 | 停止したはずのキューが生存し二重実行 | `pkill -f "<dir>/run_queue.sh"` が実コマンドライン `bash ./run_queue.sh` (相対パス) に**不一致** | 起動時に `echo $$ > queue.pid`、停止は `kill $(cat queue.pid)`。pkill 確認は別パターンで |
| 4 | eval 用バックエンドが突然死 | 共有マシン上の他プロセス掃除に巻き込まれる (8001/8002 等のポート競合圏) | eval 専用の**ずらしたポート** (8012〜) + アームごとに起動/停止を自己管理 |
| 5 | overnight 実行が 9/12 失敗、所要 3.5h | ホストの**アイドルスリープ + Thermal Emergency 強制スリープ**。プロセス凍結 → 再開時に read timeout (§6.11) 連鎖 | **無人 eval は `caffeinate -dims` 必須**。日中実行が望ましい (熱緊急は caffeinate でも防げない) |

## 4. 測定結果

### 4.1 cap A/B (四季 12 題、caffeinate 下のクリーン測定、両アーム 12/12 記録)

| 指標 | cap-off (main) | cap-on (**4096**) |
|---|---|---|
| 合格率 | **83.3%** | 66.7% |
| 平均スコア | **77.9** | 69.0 |
| 初回合格率 | 33.3% | 33.3% |
| plateau 率 | 16.7% | **33.3%** |
| 平均所要/題 | ≈4.6 分 | ≈4.8 分 |
| phase raw 最大 | 20,010+ 文字 (保存上限で打ち切り) | **12,143 文字** (cap で頭打ち = 発火確認) |

**4096 不採用の機序**: 打ち切られた attempt は schema_invalid の「捨て手番」になり、
再試行がもう一周長考するため**所要時間は縮まない**。さらに score 0 の混入で plateau 判定が
早期発火し、**best-of-N の妥協採用が倍増**。狙っていた暴走 (31k 文字級) は健全な環境の
12 題では一度も出現せず、**正常な長考に課税しただけ**だった。

→ **既定値を 8192 に修正** (観測分布 p90=13.7k 文字 / max 20k+ censored の「検閲された尾」=
真の暴走だけを切る位置)。正常運転ではほぼ発火せず cap-off 相当、暴走時のみ fail-clean に落とす
**安全弁**として採用。

注記: cap-on アームは prompt 抑止文言と同梱のため、品質差への各々の寄与は未分離
(抑止文言単独の害は考えにくいため残置)。

### 4.2 newyear A/B (#11 の確定、新年 8 題、各 7 記録)

| 指標 | 修正前 (58bfa36) | 修正後 (3e8e254) |
|---|---|---|
| 合格率 | 57.1% | **71.4%** |
| 平均スコア | 59.3 | **66.9** |
| major 違反 (`season_consistent`) | **7** | **0** |

- 修正前は plan が新年を回避して冬に流れ、新年系季語 (初日の出・門松・屠蘇) を冬で宣言 →
  辞書季との不一致 (major) を 7 回踏む軌道
- 修正後は plan=新年 → 出力 新年/鏡餅/91 点という専用ペア意図どおりの成功例を確認
- 当初仮説の「新年 plan → 春磁石転落」は両アーム 0 件 — **plan 自体が新年を出しにくい**ため
  発火条件が稀で、修正の実効は「新年経路の一貫性向上」に出た
- 留保: n=7、修正後アームは障害 #3 の並走汚染下で実行 (改善方向は一貫、断定は弱い)

## 5. 最終状態

- PR #23: cap 既定 **8192** (安全弁) + prompt 抑止文言、テスト 113 件、強制打ち切りスモーク済み
- #11/#13 (新年 few-shot): A/B で regression なし・改善方向を確認 (マージ済みの妥当性裏付け)
- eval ハーネス恒久改善: 完了判定の堅牢化 / テーマ間クールダウン / テーマ毎タイムスタンプ /
  PID ファイル停止 / アーム毎の fresh reload + 専用バックエンド (パッチは /tmp 作業コピーで検証済み。
  本体 eval.sh への反映は別 issue 推奨)

## 6. 教訓

1. **採用判断は必ず数値で**。4096 は分布から導いた「もっともらしい」値だったが、実測は有害だった
   (打ち切り→再試行のフィードバックを事前推論で見抜けなかった)
2. **thinking モデルの自己検証は設計で殺す**。プロンプトの禁止指示は 8B に効かない。
   検証器がある系では「早く出させて機械に直させる」が正しく、上限はその強制手段
3. **無人 eval チェックリスト**: 明示ロード (context 指定) / `caffeinate -dims` /
   fresh reload / クールダウン / PID ファイル / 専用ポート。どれか一つ欠けると一晩が無駄になる
4. **測定インフラの障害は測定対象の障害より高くつく**。今回 5 回の再測定のうち
   コードの問題は 0 回、全て環境・運用だった
