# 季節ドリフト / 春アトラクター 問題分析

> 対象セッション: `6a24d988f64fc884b0ea2ba3`（お題「夏の夕暮れ」）
> 成果物: [`index.html`](./index.html)（HTMLスライド。ブラウザで開く／←→で移動）

---

## TL;DR

お題「**夏の夕暮れ**」に対し、構想（Plan）は正しく `季節=夏 / 季語=蛍` を選んだのに、
最終出力は `季節=春 / 季語=花`（桜が散る歌）に転落し、**47点（合格80点）の不合格作が
「完成」として採用**された。これは単発の事故ではなく、横断52件で **非春planの37%が春へ
転落、ドリフトは100%春への一方通行** という系統的現象（**春アトラクター**）。

真因は **プロンプト先頭の few-shot 例 #1（散る桜/春/花）への regression**。
対策（**動的 few-shot**＝お題の季の例だけを見せる）を実装し、統制実験で春ドリフトの
消失を確認した。

## 2. 問題点の全リスト

### ① Plan→Compose の季ドリフト（重大）
構想 `夏/蛍` → 出力 `春/花`。validator は毎試行で正しく検出している：
- `season_matches_plan` −30（構想の季節と不一致）
- `kigo_matches_plan` −20（構想の季語と不一致）
- 試行2では `no_other_kigo_cross` −30（本文に宣言外の「蛍」が残存）

**検出は機能している。問題はモデルが従わないこと（8Bの指示追従の弱さ）と矯正できないこと。**

### ② 真因: few-shot 例 #1 への regression
プロンプト先頭の few-shot #1 は「お題:散る桜 / 春 / 花 / "花の散るらむ" / emotion『自然の理への諦観』」。
今回の出力は結句 **「自然の理かな」**＝ #1 の emotion からの**直接コピー**。image「桜の花が散っていく」・
emotion「儚く散る花への哀れみ」も #1 のほぼ言い換え。**モデルは構想を捨てて先頭の春の例に collapse した。**

### ③ RAG が「春」アンカーを注入（増幅要因）
季語「蛍」はコーパスにexact 0件 → 季節=夏フォールバックで2首注入。うち1首が
持統天皇「**春過ぎて** 夏来にけらし…」。**参考歌の冒頭が「春過ぎて」**で、#1と合わせ春磁石が2つ。
RAGが春ドリフトを助長した可能性。

### ④ refine回復失敗 ＋ 不合格を無警告で採用
- 4試行すべてが春/花のbasinに留まり、スコアは乱高下（試行2で17へ悪化）= best-of-Nが誤attractorに捕捉。
- 47点（<80）の歌を最終提示。fail-softでbestを返す設計だが、**「規定未達」の警告が無い**。

### ⑤ validatorの検出ギャップ ＋ 永続化バグ
- `theme_time_mismatch` は**矛盾**しか見ない → 出力に時刻語が無く「夕暮れ」を全く詠めていない**欠如**は見逃し。
- お題遵守は plan 整合経由でしか効かない → **planも春に流れたら何も捕まえられない**構造欠陥。
- **コードバグ**: `tasks.py` の `max_refines_reached` 分岐が `best_score`/`score_history` を保存しない
  （`plateau_reached` 分岐は保存する）。DB上 `best_score=undefined` となり事後分析を妨げた。

### ⑥ 形式の小欠点（残存したまま採用）
4句目「哀しさのみ」= 6拍（字足らず）。試行0で `schema_invalid`（emotion欠落）= JSON生成の不安定さ。

## 3. これは単発ではない — 横断52件

### plan季 → 出力季 の遷移行列

```
plan＼出力   春   夏   秋   冬     正答率
  春         10    ·    ·    ·     10/10 = 100%   ← 春は完全な吸着点
  夏          8   10    ·    ·     10/18 =  56%
  秋          4    ·    6    ·      6/11 =  55%   (+∅ 1)
  冬          2    ·    ·    6      6/8  =  75%
  ∅(抽出失敗) 5    ·    ·    ·      0/5  =   0%   ← 全部春へ
```

- **非春plan→春: 37%（14/37件）**
- **春plan→春: 100%（10/10）**（春は出られない・吸い込む非対称な引力）
- **夏/秋/冬への横滑り: 0件**（誤りは必ず春へ＝一方通行）
- **plan抽出失敗→春: 100%（5/5）**（迷うとデフォルトで春）

### few-shot 指紋（どの例が写されたか）

| few-shot | ヒット |
|---|---|
| #1 散る桜（春/花） | **4件** |
| #2 夏の夜（夏） | 0件 |
| #3 秋風（秋） | 0件 |
| #4 冬（冬） | 0件 |

**#1のみが写されている** → 「季節の合う例を写す」のではなく「例#1そのものへの固着」。

### ガードの時系列（検出はするが盲点があった）
- 〜06-03（ガード未実装/JSON-plan盲点期）: ドリフトが 84/89/82/97点で「合格」扱い（**お題違反が高得点で確定**）。
- 06-04〜（テキストplanで発火）/ 06-07にJSON-plan盲点クローズ: 以降は 35〜50点で検出される。
- ただし**検出できても矯正できず**、47点の不合格作が提供される結果は変わらない。

## 4. 真因と対策

**真因 = 春アトラクター**。プロンプト先頭の few-shot #1（散る桜/春/花）が最も鮮烈で、
8Bがお題に迷うとそこへ collapse する。これまでの修正（ガード追加・JSON抽出）は全て
**「検出」側**で、原因（磁石）を断っていなかった。

### 対策: 動的 few-shot（実装済み）
plan の季に**一致する例1ペアだけ**を compose に見せ、他季（特に春）の磁石を隠す。

| ファイル | 変更 |
|---|---|
| `prompts.py` | `FEW_SHOT_BY_SEASON` + 純関数 `select_few_shot(season_hint, dynamic=)`、`build_compose_messages` に `season_hint`/`dynamic_fewshot` 引数 |
| `config.py` | `DYNAMIC_FEWSHOT = env_bool("TANKA_DYNAMIC_FEWSHOT", True)` |
| `tanka.py` | `compose_base()` で config 値を compose に伝達 |
| `docker-compose.yml` | `TANKA_*` パススルー口を追加（eval ablation が実際に効くように） |
| `tests/test_prompts.py` | 新規10ケース（選択ロジック＋並べ替え事故の安全網） |

検証: **pytest 69 passed**、import OK。

### 統制実験（compose段の単離 A/B）
同一 plan・同一 plan_constraint で **few-shot OFF/ON だけ**を切替（OFF/ONペア隣接・rep-major）。
非春テーマ4件（夏の夕暮れ/紅葉の散る山道/名月を仰ぐ宵/冬の寂寥）× 3反復。
production と同一パース（`stream_completion → split_harmony → parse_tanka_json`）。

**結果（計24試行、parse成功 24/24）:**

| 条件 | 春へ転落 | 季ドリフト |
|---|---|---|
| OFF（四季全部・従来） | **8/12 (67%)** | 8/12 |
| ON（動的） | **0/12 (0%)** | 0/12 |

テーマ別「春へ転落」: 夏の夕暮れ `OFF 3/3 → ON 0/3` ／ 紅葉の散る山道 `OFF 2/3 → ON 0/3`
／ 名月を仰ぐ宵 `OFF 2/3 → ON 0/3` ／ 冬の寂寥 `OFF 1/3 → ON 0/3`。
**1ペア提示でも parse 失敗は増えず（format 劣化なし）** = 「四季を揃えないと壊れる」という旧前提は否定された。

> 結果は本ディレクトリではなく `app/backend/eval/results/fewshot_isolation.{log,json}` に保存。
> スコア要約は `index.html` の対策スライドに反映。
> 再現: `docker compose exec backend uv run python eval/fewshot_isolation.py`

## 5. 帰属マップ（どの層を直せば効くか）

| 層 | 問題 | 状態 |
|---|---|---|
| モデル挙動 | few-shot #1 への collapse（真因） | ✅ 動的few-shotで対策・実証（OFF 8/12→ON 0/12） |
| RAG | 春アンカー（「春過ぎて」）注入 | ✅ 測定済→**ドリフト要因ではない**。下記参照 |
| validator | 時刻の欠如・お題直接照合なし | ⬜ 未対応（positive rule案） |
| コード（バグ） | `max_refines`でbest_score未保存 | ⬜ 要修正 |
| 運用 | 不合格作を無警告で採用 | ⬜ UIに「未達」バッジ案 |

### 補足: RAG 春アンカーの追試（2026-06）

「春過ぎて」注入が残留ドリフトを起こすか、metadata-first 整形が効くかを統制実験で検証
（dynamic few-shot ON 固定・「春過ぎて」注入 9/9・計27試行）:

| 条件 | 季ドリフト | 季語が plan 維持 |
|---|---|---|
| `rag_off` | 0/9 | 4/9 |
| `rag_legacy`（旧・「春」裸） | **0/9** | **7/9** |
| `rag_meta`（新・metadata-first） | 0/9 | 4/9 |

**結論**: dynamic few-shot で主磁石を消した後は、RAG の春アンカーは現行整形のままでも季ドリフト 0。
よって #1（RAG 春除外）は**ドリフト対策としては不要**。metadata-first は季の利点が無く、例の季語
「夏の夜」を目立たせて**季語コピーをむしろ誘発**したため**採用見送り**。実装と統制実験ハーネスは
[issue #6](https://github.com/nrm176/tanka-llm-jp/issues/6) で削除済み（測定データはこの表に保存）。
