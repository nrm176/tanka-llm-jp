## 2. 最重要知見: スコアは確率変数（best-of-N であって反復改善ではない）

同一お題が run をまたいで大きくぶれることを観測：

| お題 | run 横断のスコア | 振れ幅 |
|---|---|---|
| 散りゆく桜 | 70 → 97 → 100 | **30** |
| 通学路の桜並木 | 97 → 76 | 21 |
| 海辺の街を見下ろす坂道 | 95 → 89 | 6 |

### なぜぶれるか（コード上の理由）

`tanka.py` の refine ループは、各 attempt で前の歌を**編集**するのではなく、
critique を見て**ゼロから別の歌を生成**する。さらに最終結果は全 attempt の
**best score を採用**する。つまりこれは：

```
反復改善 (iterative refinement)  ではなく
best-of-N サンプリング           である
```

score 推移は単調降下ではなく **random walk のピーク取り**。
「6 回 refine して 70」と「1 回で 97」は、改善努力の差ではなく **引きの差**。

### 含意

- **avg_final_score の単一 run 比較は危険**。`compare.sh` は警告を出すよう修正済み
- 正しい評価には **同一お題の複数 run で mean±std** を取る必要がある → `eval-repeat.sh`
- 研究記述では "iterative refinement" と書かず "validator-guided **best-of-N sampling**" と書くべき

### variance 実測 (eval-repeat.sh, 散りゆく桜 ×6) — LM Studio fresh reload 後

| run | score | attempts |
|---|---|---|
| 1 | 90 | 1 |
| 2 | 94 | 1 |
| 3 | 80 | 2 |
| 4 | **75** | **6** ← 最多改稿で最低スコア |
| 5 | 95 | 3 |
| 6 | 100 | 2 |

```
mean   = 89.0
stdev  = 9.6  (標本)   /  8.8 (母)
range  = 75 - 100  (25 点!)
```

**同一お題で stdev ≈ 9.6、レンジ 25 点。** これが評価系の最重要数値。

#### 決定的な観測

- **run 4 は 6 回改稿して 75（最低）、run 1 は 1 回で 90**。改稿回数とスコアは無相関。
  → "iterative refinement" ではなく **best-of-N sampling** であることの動かぬ証拠
- ベースラインの「avg 90」は **1 サンプル**。同じ条件で 75 にも 100 にもなりえた

#### A/B 比較のノイズ下限（この stdev から導出）

| 比較単位 | 平均の標準誤差 | 偶然生じうる差 (2SE) |
|---|---|---|
| 単一テーマ・単一 run | ±9.6 | ±19 |
| 8 テーマ平均 | ±3.4 | **±6.8** |
| 50 テーマ平均 | ±1.4 | **±2.7** |

→ **8 テーマ eval では、平均スコアが ±6.8 以内の差は sampling noise**。
有意な改善を主張するには **50 テーマ + 複数 run**、または **テーマあたり複数 run の平均** が必要。
`compare.sh` の「全項目改善」表示（partial 7/8 vs clean 8/8、+2.86 点）は **このノイズ幅以下** であり、
品質向上ではなく運の差だったと確定する。

## 4. 評価アルゴリズムの構造的限界（コード由来）

`validator.evaluate()` は `score = max(0, 100 − Σ weight)` の **加法的減点モデル**。
詳細な考察は本リポジトリの会話ログ参照。要点：

- **報酬項がゼロ** — 欠陥の不在しか測れない。情感・調べ・余韻など「質」は未評価
  （`image`/`emotion` は非空チェックのみ、内容は不問）
- **0 への張り付き** — 違反過多で全部 0 になり勾配を失う（海辺の街が途中 score 0）
- **重み・閾値が無較正の hand-tuned 値** — 「80=良い短歌」の根拠なし
- **`repeated_word` が重複に甘い** — 3文字窓・1件返しのため `光`×3 でも軽微 (-3)
- **violation_frequency は全 attempt 横断** — 最終成果でなく探索過程の分布。難テーマにバイアス

## 5. 環境的制約: LM Studio の不安定性（host 側、コードではない）

このホストで LM Studio は sustained load 下で性能が大きく oscillate する：

```
fresh:    ~15s/call (健全)
degraded: ~3.5min/call + 時折 HTTP 400 (context rejection)
idle後:   回復
```

- 自動 eval が大きいプロンプトを連続投入 → KV キャッシュ/context 圧迫 → 劣化
- **コードは堅牢化済み**（両 timeout/fallback で無限ハングは起きない）が、
  劣化中は 1 テーマ 7 分かかるなど **eval が遅く不安定になる**
- 自前の診断 streaming 呼び出しが **load を上乗せして劣化を悪化させた**（教訓: eval 中は probe しない）

### 推奨運用

- 複数 variant を回す A/B 実験は、**モデルを fresh reload 後**、できれば**専用ターミナル**で
- eval 中はバックグラウンドの LM Studio 診断を避ける

## 5.5 self-critique A/B 実験 (Phase 3 第一弾) — 結論不能 + 方法論的教訓

self-critique フェーズ (Phase 1 B4, +1 LLM call/生成) の費用対効果を測った。
16 テーマ × {ON, OFF} の blocked A/B。

| 指標 | sc-ON | sc-OFF | 差 |
|---|---|---|---|
| 平均スコア | 75.06 | 79.75 | +4.69 (OFF) |
| 初回合格率 | 37.5% | 6.2% | ON |

### 判定: 有意差なし + 交絡あり

- **ノイズ下限 ±4.8 (n=16 の 2SE) に対し観測差 +4.69 → 統計的に区別不能**
- 交絡チェック (前半/後半分割) が決定的:

```
A(sc-on)   前半8=88.1  後半8=62.0   ← LM Studio 劣化で後半クレーター
B(sc-off)  前半8=83.3  後半8=76.3   ← 後半 7 点低下のみ
```

- 全体平均の差は **A 後半の LM Studio 劣化** に起因。self-critique の効果ではない
- **前半だけ見ると sc-ON が上 (88.1 vs 83.3) で全体結果と逆符号** → 効果の符号すら不明

### 方法論的教訓 (実験そのものより価値がある)

1. 事前登録したノイズ下限基準が機能 (+4.69 を有意と誤認せず却下)
2. 前半/後半分割で「環境劣化 vs 実効果」を切り分けられた
3. **blocked A/B は不安定ハードでは信頼できない** → 次は paired/interleaved 設計が必須:
   - 各テーマで ON/OFF を交互に実行 (両者が同じ LM Studio 状態を経験)
   - または各テーマ複数 run の平均で per-theme 分散を潰す
   - fresh reload + run 間インターバル

→ **self-critique の存続判断は保留。** 現データでは「効果は測定ノイズより小さい」としか言えず、
コスト (+1 call) を正当化も否定もできない。paired 再測定が必要。

## 5.6 self-critique paired A/B 再測定 (2026-09-05) — 判定不能。ただし副産物が本命

§5.5 の「保留」を解くための再測定。`eval-paired.sh` で **お題ごとに ON/OFF を ABBA 交互実行**
(per-request `self_critique` 上書き)。50 題、n=49 pair (1 題は LM Studio 500 で片腕欠落 → 除外)。
事後検証: 両 arm とも `phases` の self_critique 有無が期待どおり (mismatch 0/99)。総計算時間 8.3 h。

| 指標 | sc-ON | sc-OFF | 差 |
|---|---|---|---|
| 平均スコア | 77.6 | 78.3 | **−0.67** |
| 2SE(Δ) | — | — | **12.75** |
| 勝敗 | 25 勝 | 21 勝 | 3 分け |
| 平均所要 | 336 s | 275 s | **+61 s (+22%)** |
| 平均 attempt | 2.2 | 2.5 | −0.3 |
| score 0 | 7/49 | 5/49 | +2 |

### 判定: **判定不能** (|Δ| 0.67 ≪ 2SE 12.75)

ただし今回は「効果があるとしても小さい」の**上限**が付いた: score 0 を含まない 37 pair では
mean Δ **+1.11**、2SE **3.66** → 破綻しない生成に限れば **実効果は ±3.7 点以内**。
一方 **コストは +22% で確実**。「品質差は測れないがコストは確実」という非対称が結論。

### 方法論的発見 1: paired 設計は分散を減らさなかった

arm 間相関 **r = +0.022**、分散削減 **+1%**。スコアを決めるのは「お題の難易度」ではなく
**生成ごとの引き** (§2 の best-of-N 再確認)。paired は **LM Studio 劣化に対する防御**としては
機能した (下記) が、**分散削減は期待できない**。今後の A/B は paired を維持しつつ、
検出力は n か「0 点の撲滅」で稼ぐしかない。

### 方法論的発見 2: ノイズ下限は ±2.7 ではなく **±12.75** (4.7 倍)

§2 の ±2.7 は「1 お題を反復した stdev 9.6」から導いており、**全生成が有効スコアを返す前提**だった。
実際の 50 題では per-arm SD が **30〜33**。差の分散の **94% が score 0 由来**。この分散での検出力:

| 検出したい差 | 必要な題数 (現状) | 0 点を撲滅した場合 |
|---|---|---|
| 10 点 | 80 | 5 |
| 5 点 | 318 | 20 |
| 3 点 | 885 | 55 |

**§2 の ±2.7 を A/B の判定基準に使ってはいけない** (0 点を除いた場合のみ近い値になる)。

### 方法論的発見 3: 前半/後半チェックは季節ブロックと交絡する

`eval_themes.json` は春→夏→秋→冬→新年→hard の順。両 arm とも後半が +8 点だが、これは
劣化からの回復ではなく**春ブロックが最難**だから (sc-on 58.8 / sc-off 71.3、0 点 4 件)。
劣化検査は絶対値ではなく **両 arm の前後半差が対称か**で見る (今回 +8.7 / +7.3 = 対称 → 交絡なし)。

### 本命の発見: score 0 の正体は「閉じ括弧 1 個の欠落」

全 98 生成中 **12 本 (12%) が score 0**、すべて `schema_invalid`。原因はモデルが JSON の
**最後の `}` を出力しない**こと。成功生成は `..."\n}` で終わるのに対し、失敗生成は `..."` で終わる。
その結果 `parse_tanka_json` の `rfind("}")` が **lines 配列内の最後の要素の `}`** を拾い、
不均衡な slice になって落ちる (エラーは「Expecting ',' delimiter」で JSON の中身の問題に見えるが、実体は末尾切れ)。

未閉じ括弧を補う救済 (#65 で実装) を当てると **schema_invalid の raw 71/86 (83%) が復元でき**、
**0 点生成 12 件のうち 9 件 (75%) が救済される**。期待利得は平均 **+8.1 点** (77.8 → 85.9、
0 点率 12% → 3%) で、self-critique の効果 (±3.7 以内) の **2 倍以上**。
0 点が減れば A/B の検出力も上がる (上表)。→ **issue [#65](https://github.com/nrm176/tanka-llm-jp/issues/65)**

> **訂正 (2026-09-06)**: 初出時に「94% / 10 件 / +9〜11 点」と記載したが、これは調査用プロトタイプの
> 計測ミスだった。プロトタイプは「`json.loads` が通る」ことを救済成功と数えていたため、
> **末尾切れではないケース (構文的には valid だがキー名が誤っている) を成功に含めていた**。
> 実装版で数え直した値が上記。差の 10 件はすべて **`emotion` キーの綴り誤り** (`emoton` 9 件 /
> `emotio n` 1 件) で、括弧補完では直らない別種の不具合 → issue [#68](https://github.com/nrm176/tanka-llm-jp/issues/68)

> **追記 (2026-09-06)**: #68 (綴り誤りの alias 受け入れ) を併せると、この run の
> **schema_invalid raw 81/86 (94%) が復元でき、0 点生成は 12/12 (100%) が救済される**。
> 期待平均は **77.8 → 88.6 (+10.7 点)**、**0 点率 12% → 0%**。
> 0 点は差の分散の 94% を占めていたので、以後の A/B は §5.6 の検出力表の「0 点を撲滅した場合」
> の列 (5 点差の検出に 20 題) が使える見込み。**#66 の再測定はこの状態で行うこと**

### 結論

1. **self-critique**: 品質差は測定不能 (±3.7 以内)、コスト +22% は確実 → 既定 OFF 化を提案 ([#66](https://github.com/nrm176/tanka-llm-jp/issues/66))
2. **次にやるべきは self-critique の微調整ではなく `schema_invalid` の撲滅** ([#65](https://github.com/nrm176/tanka-llm-jp/issues/65))。
   同じ 8 時間を使うなら、こちらのほうが桁違いに効く。#65 を入れてから self-critique を測り直すのが合理的
3. 実行中に compose で LM Studio 500 が 1 件 (98 生成中)。plan/compose には refine と違い fallback が無く
   タスクごと失敗する → [#67](https://github.com/nrm176/tanka-llm-jp/issues/67)

## 6. モデル A/B: gemma-3-27b vs llm-jp-4-8b-thinking (2026-06-14)

**問い**: non-thinking の google/gemma-3-27b を既定モデルに採用すべきか
(背景: qwen3-swallow 不適合インシデント `app/docs/model-compat-qwen3-swallow.md` 推奨①)。
**設計**: 四季×3=12題 (`eval_themes_x12.json`)、各アーム fresh load(32k)+切替検証、caffeinate 下。
**事前登録判定基準**: 主指標 avg_final_score、n=12 ノイズ下限 ±5.6、|Δ|≤5.6 は判定不能。

| 指標 | llm-jp | gemma-3-27b | 判定 |
|---|---|---|---|
| **avg_final_score** | 77.17 | 80.00 | **+2.83 → ノイズ内 (判定不能)** |
| 総合合格率 | 83.3% | 83.3% | 同 |
| 初回合格率 | 75.0% | 41.7% | gemma 劣 (有意) |
| 平均 attempt | 1.58 | 3.00 | gemma 約2倍 (有意) |
| 違反総数 (全attempt) | 31 (crit9/min22) | **179** (crit56/maj6/min117) | gemma 約6倍 |
| └ mora 系 (count+off_by_one) | 6 | **88** | gemma 圧倒的に弱い |
| └ kigo 規律 (no_other+in_dict) | 1 | **57** | gemma 弱い |
| └ schema_invalid | 9 | **0** | gemma 勝 (thinking 暴走なし) |
| 90-100 点の歌 | 6 | 3 | llm-jp 優 |
| 所要時間 (12題) | ~50分 | **~14分** | gemma 約3.5倍速 |

**劣化交絡チェック**: 両アームとも後半≥前半 (llm-jp 59.7→94.7、gemma 75.3→84.7)。沈み込みなし=測定有効。

**結論 (判定不能 + 二次指標の明確な差)**:
- **主指標 avg_final_score は +2.83 でノイズ内 → gemma は品質で llm-jp を上回らない**
- ただし二次指標 (イベント count、ノイズではない) は明確: gemma は **拍数 (88 vs 6)・季語規律 (57 vs 1)**
  という**短歌特有スキルで決定的に弱く**、同じ合格率に達するのに約2倍の refine を要し、best-of-N が
  より多くの試行から拾うことで final score の見かけ上の同点が成立している。90-100 の名歌は llm-jp が倍
- 故障モードが相補的: **llm-jp = 一発精度高いが稀に thinking 暴走で 0 点** /
  **gemma = 暴走なし・高速だが拍数/季語が雑で validator に依存して 80 点台に滑り込む**

**採否**: **既定は llm-jp 継続**。gemma-3-27b は #20/#21 の**セッション固定モデルとして残す**
(高速ドラフト用途・llm-jp の暴走が問題な場面の代替)。両者は補完関係であり置換ではない。

### 6.1 追試: gpt-oss-20b を加えた 3モデル統制比較 (2026-06-14)

同一 `eval_themes_x12.json` で gpt-oss-20b を測定し 3モデル確定:

| model | avg | first-pass | attempts | mora違反 | schema | zero率(観測) | 90-100 |
|---|---|---|---|---|---|---|---|
| llm-jp | 77.2 | **75%** | **1.58** | **6** | 9 | **17%** | 6 |
| gemma-3-27b | 80.0 | 42% | 3.00 | 88 | 0 | 0% | 3 |
| gpt-oss-20b | **84.5** | 8% | 3.42 | 135 | 1 | 0% | 6 |

**発見**: avg 順位 (gpt-oss>gemma>llm-jp) が素の実力順位 (llm-jp≫gemma>gpt-oss) を**反転**。
validator-guided best-of-N では最終品質 = refine 応答性 × 無事故性であり、一発の上手さではない。
gpt-oss avg +7.3 (vs llm-jp) はノイズ下限 ±5.6 超だが、(a) 単一 run (b) gpt-oss は後半低下
(89.3→79.7) のため確認 run 推奨。**llm-jp の質の天井 (zero 除く 10 首 ~92.6) は依然最高**。
詳細・選択指針は `app/docs/model-characteristics.md`。
